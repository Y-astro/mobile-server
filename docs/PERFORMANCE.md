# Transfer measurements — 22 October 2026

**Verdict: throughput improvement on the mobile-data path is unverified.** The requested six-file queue and security limits are implemented and tested. A higher mobile upload/download speed is not promised: the link changed substantially during measurement. No kernel or carrier setting was changed without evidence of benefit.

The primary metric was sustained end-to-end FileBrowser throughput with correct generated bytes, 16 MiB per file, at one, two and six concurrent files. Existing source/settings were captured privately; only aggregate results are published in [measurements.json](measurements.json). Downloads checked SHA-256. Resumable TUS was independently tested for six concurrent files, including partial PATCH, HEAD offset, resume and final SHA-256.

The repeat of the original six-file mobile upload was stopped once sustained congestion made it unsuitable for a comparison. The updated six-file mobile attempt did not complete (broken pipe amid the congested path and subsequent server configuration validation); no throughput is reported for it. The USB numbers are diagnostic capacity, not a before/after mobile speed improvement. The USB diagnostic uses the same Caddy → admission gateway → FileBrowser path with networking transported by ADB.

The laptop was USB-tethered to OnePlus mobile data. Tailscale confirmed direct IPv6 peer transport to the Redmi, rather than DERP. While uploads stalled, established TCP connections showed 2–3 second RTTs, retransmissions and megabytes waiting to send, versus approximately 30–35 ms minimum RTT. Even Tailscale netcheck's independent internet probes took around 3.8 seconds. During another check the laptop received no response to three ICMP probes, while the Redmi's home connection returned 12.9–15.2 ms replies to the same target. ICMP loss alone does not locate a fault, but together these observations strongly point to congestion/queueing on the laptop/mobile-data side of the path.

Phone `top` samples during transfers showed roughly 579/800 to 693/800 percent aggregate idle CPU (eight cores), 0% I/O wait, Tailscale about 36–46% of one core, Caddy about 7%, and FileBrowser about 4% in the slow sample. These are samples, not complete per-core profiles; they do not show CPU or storage saturation as the main cause of the observed slowdowns.

## Decisions

- Keep the requested six-file queue as a feature, with six/user and eight/global server write limits. It is not a proven speed optimization for saturated mobile data; two streams were faster than six in one original-site trial. Each TUS file still has one stream to preserve ordering.
- Keep native FileBrowser and bounded streaming. Their measured local HTTP capacity is far above the mobile path. Admission, cancellation release, resource locking, resumable offsets and integrity pass their checks.
- Keep idle deadlines instead of short whole-file time limits. Caddy full-duplex error handling fixes stalled error responses; the live terminal continued working after 65 seconds idle.
- Do not enable Tor for transfers, force a relay, increase parallelism without a cap, disable encryption, or apply guessed TCP/sysctl settings. None addresses the measured carrier congestion, and Tor would introduce a different, slower route.
- Direct connectivity is already the preferred network path. The Redmi currently associates at 2.4 GHz / 144 Mbps; a 5 GHz AP with adequate signal is an optional next Wi-Fi experiment. It was not changed remotely because there was no verified way to select the saved 5 GHz association without reprovisioning credentials. The observed simultaneous cellular-side latency makes it unlikely that changing Redmi Wi-Fi alone resolves the severe stalls.

A meaningful next speed comparison needs stable mobile reception, no competing transfers and repeated interleaved trials on that same connection. Compare another client network (for example good Wi-Fi or a different carrier) to separate carrier limitations from the home uplink. Actual capacity is bounded by the slowest uplink/downlink, radio conditions, queueing and Tailscale's Android implementation. No software setting here can guarantee the initial 9 MB/s burst indefinitely.
